# Release 1.0 — Campaign Simulator

## Campaign Simulation Foundation

- Added `CampaignSimulationService`.
- Added `CampaignSimulationServiceImpl`.
- Added immutable `CampaignSimulationResult`.
- Campaigns can coordinate all their patrol simulations.
- Patrols are executed by patrol date and identifier.
- Tactical execution remains delegated to `SimulationService`.
- Existing tactical evaluation and persistence are reused unchanged.
- Empty campaigns return a valid result with zero patrols.
- Campaign execution currently follows a synchronous fail-fast strategy.
- Added automated tests for orchestration order, empty campaigns,
  missing campaigns and interrupted execution.
- Added ADR-001 documenting campaign-to-patrol delegation.

## Campaign Progression

- Added immutable `CampaignProgress`.
- Added `CampaignProgressService`.
- Campaign progress is derived from existing patrols and persisted
  simulation records.
- Completed patrols are counted distinctly.
- Repeated simulations do not increase completion incorrectly.
- Added total, completed and pending patrol counts.
- Added completion percentage rounded to two decimal places.
- Added campaign completion status.
- Empty campaigns report zero-percent progress and remain incomplete.
- Integrated campaign progression into `CampaignSimulationResult`.
- Added ADR-002 documenting derived campaign progression.

## Campaign Statistics

- Refactored the existing campaign statistics module.
- Campaign statistics now use persisted `SimulationRecord` data.
- Added distinct completed-patrol metrics through campaign progression.
- Added total historical simulation count.
- Added successful, partially successful and failed simulation totals.
- Added campaign success rate.
- Added average tactical mission score using real persisted scores.
- Added contacts detected and contacts lost totals.
- Added intelligence-gathered totals.
- Added incident totals.
- Removed the unused fixed `averageRisk` value.
- Removed estimated scoring based on `PatrolResult`.
- Preserved the existing campaign statistics REST endpoint.
- Added service, mapper, controller and repository test coverage.

## Campaign Lifecycle Design

- Defined the Release 1.0 campaign lifecycle.
- Preserved the existing `ACTIVE`, `FINISHED` and `ABANDONED` statuses.
- Defined valid and invalid campaign transitions.
- Defined `FINISHED` and `ABANDONED` as terminal states.
- Defined campaign completion through derived campaign progression.
- Established that only active campaigns may execute new simulations.
- Established that empty campaigns cannot be finished.
- Decided not to introduce State Pattern before state-specific behaviour
  justifies it.
- Added ADR-003 documenting lifecycle transition architecture.
- Added the campaign lifecycle design document.
- Added `CampaignLifecycleService`.
- Added `CampaignLifecycleServiceImpl`.
- Added explicit campaign finish transition.
- Added explicit campaign abandonment transition.
- Campaigns can only transition from `ACTIVE`.
- Finished and abandoned campaigns are treated as terminal.
- Finishing a campaign requires completed campaign progression.
- Empty campaigns cannot be finished.
- Added `InvalidCampaignTransitionException`.
- Invalid lifecycle transitions are mapped to HTTP 409.
- Added unit coverage for valid transitions, terminal-state rejection,
  incomplete progression, empty campaigns and missing campaigns.

## Campaign Execution Status Validation

- Added lifecycle validation to campaign simulation orchestration.
- Only active campaigns can execute patrol simulations.
- Finished campaigns cannot be simulated again.
- Abandoned campaigns cannot be simulated.
- Lifecycle validation runs before patrol retrieval.
- Reused the existing `InvalidCampaignTransitionException`.
- Avoided duplicate campaign repository lookup.
- Added lifecycle and campaign-orchestration test coverage.

## Campaign Lifecycle REST API

- Added `PATCH /api/v1/campaigns/{id}/finish`.
- Added `PATCH /api/v1/campaigns/{id}/abandon`.
- Lifecycle endpoints reuse `CampaignLifecycleService`.
- Lifecycle responses use the existing `CampaignResponseDTO`.
- Invalid transitions return HTTP 409.
- Missing campaigns return HTTP 404.
- Lifecycle endpoints remain protected by JWT.
- Added controller, security and integration coverage.
- Completed the Campaign Lifecycle section of the Release 1.0 roadmap.

## Campaign Simulation REST API

- Added `POST /api/v1/campaigns/{id}/simulate`.
- Added `CampaignSimulationController`.
- Added `CampaignSimulationResponseDTO`.
- Added `CampaignProgressResponseDTO`.
- Added `CampaignSimulationMapper`.
- Campaign simulation responses include campaign progress.
- Campaign simulation responses include ordered patrol results.
- Patrol results reuse the existing `SimulationMapper`.
- Missing campaigns return HTTP 404.
- Invalid campaign lifecycle states return HTTP 409.
- Campaign simulation remains protected by JWT.
- Added mapper, controller, security and integration coverage.

## Campaign Execution Persistence

- Added `CampaignExecution`.
- Added `CampaignExecutionStatus`.
- Added campaign execution repository.
- Added campaign execution persistence service.
- Every accepted campaign simulation creates a running execution record.
- Successful orchestration records completed execution metadata.
- Failed orchestration records partial patrol completion.
- Failure messages are persisted safely and truncated to the column limit.
- Tactical simulation records remain independent.
- Added service, repository and orchestration test coverage.
- Added ADR-004 documenting campaign execution persistence.

## Campaign Execution History API

- Added paginated campaign execution history.
- Added `GET /api/v1/campaigns/{campaignId}/executions`.
- Added `CampaignExecutionResponseDTO`.
- Added `CampaignExecutionMapper`.
- Added campaign execution history service.
- Added campaign existence validation.
- Added default ordering by `startedAt DESC`.
- Empty campaign execution history returns an empty page.
- Missing campaigns return HTTP 404.
- The endpoint remains protected by JWT.
- Added mapper, service, repository, controller, security and integration coverage.

## Campaign Timeline

- Added unified campaign timeline.
- Added TimelineAssembler.
- Added Campaign Timeline REST API.
- Combined campaign execution history and tactical simulation history.
- Added controller, service, integration and security coverage.

## Dynamic Patrol Generation

- Added rule-based campaign patrol generation.
- Added `PatrolGenerator`.
- Added `CampaignPatrolGenerationService`.
- Added `POST /api/v1/campaigns/{campaignId}/generate-patrols`.
- Patrols are generated only for active submarines.
- Finished and abandoned campaigns reject patrol generation.
- Existing campaign assignments prevent duplicate patrol creation.
- Repeated generation requests are idempotent.
- Generated patrols use the campaign start date.
- Generated patrols use `DETERRENCE_PATROL`.
- Generated patrols use `North Atlantic` as the default area.
- Added repository, generator, service, lifecycle, controller, security
  and integration coverage.

## Rule-Based AI Opponent

- Added deterministic opponent decision modelling.
- Added `OpponentDecision`.
- Added `OpponentDecisionType`.
- Added `OpponentDecisionRules`.
- Added `OpponentDecisionEngine`.
- Reused the existing `DetectedContact`, `ThreatLevel` and contact
  confidence data.
- Added `IGNORE`, `MONITOR`, `INVESTIGATE` and `INTERCEPT` decisions.
- Added opponent-decision to tactical-behaviour mapping.
- Replaced random contact-behaviour resolution with deterministic rules.
- Preserved the existing `ContactBehaviourResolver` contract.
- Integrated opponent decisions with `ContactBehaviourPhase`.
- Added model, rules, engine, mapper, resolver and pipeline integration
  coverage.
- Completed the final functional milestone of the Campaign Engine.
